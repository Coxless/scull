## 要約(まずここを読む)

- **言語 Scull**:参照を持たない「値だけ」の言語(可変値セマンティクス)。副作用は、引数かスコープで受け取った**能力**だけで起こせる。能力は型に `/ {Fs}` のように現れ、エフェクトハンドラで実装を差し替えられる。unsafe も `Raw` という能力として扱う。トレーシング GC は使わない。
- **OS Coxless**:フレームカーネルとケーパビリティ OS を組み合わせる。**システムコールはエフェクト、カーネルはそのハンドラ**。権限は渡された能力だけで、グローバルなファイル空間も POSIX 互換もない。
- **核心**:言語の型に書かれた能力と、OS が与える権限(将来はハードウェアの CHERI 能力)を、同じ概念の層として扱う。
- **実装**:コンパイラは Rust で書く。Scull から C を生成し、clang で RISC-V 64 向けにビルドして、QEMU virt で動かす。

---

## 0. 名前の由来

ボート競技の用語から取った。

- **Scull(スカル)**:1人が左右2本のオールを漕ぐ種目。言語と OS という2本を1人で漕ぐこのプロジェクトを表す。
- **Coxless(舵手なし)**:全体に指示を出すコックスがいない艇。全体を支配する権限(アンビエント権限)を持つ者がいない OS を表す。
- **Sweep 原則**:スイープは1人が1本のオールだけを持つ種目。各部品が必要な能力だけを持つ「最小権限」の原則をこう呼ぶ。

## 1. 前提と「革新性」の定義

- 目的は趣味と学習。1人で数年かける規模を想定する。
- 「革新的」とは、最新研究で有望だがまだ主流に入っていないアイデアを選び、**言語と OS を同じ人が同時に設計できる立場**を活かして組み合わせること。
- 個々の部品はどれも既存研究にある。新しさは組み合わせ方と、言語・OS・ハードウェアをまたぐ一貫性にある。

## 2. 研究動向の要点(主に 2020–2025)

### 言語側

| テーマ | 代表的な研究 | 要点 | 取り込むもの |
|---|---|---|---|
| エフェクト＝能力 | Effekt (OOPSLA'20 〜 ICFP'25 / OOPSLA'25) | エフェクト型は「どの能力を文脈から受け取る必要があるか」を表す。ハンドラはレキシカル | I/O・メモリ確保・MMIO などを能力として型で追跡する |
| キャプチャ検査 | Scala 3 / System Capless (OOPSLA'25) | 値が捕捉している能力を型に載せる。標準コレクション全体に適用済み | クロージャやデータ構造に能力が漏れるのを静的に防ぐ |
| 可変値セマンティクス | Hylo(旧 Val) | 型はすべて値型で、参照型がない。ライフタイム注釈も借用チェッカもなしで安全 | Rust より実装も学習も簡単な安全性モデル |
| 再利用つき参照カウント | Perceus / Koka (PLDI'21) | 純粋関数的なコードが実行時にはインプレース更新になる (FBIP) | トレーシング GC なしのヒープ管理 |
| 線形ゴースト型による検証 | Verus (SOSP'24)、Atmosphere (SOSP'25)、VeruSAGE (2025) | SMT で Rust を検証。検証済みカーネルの実例あり | 将来の拡張として仕様構文を予約する |

### OS 側

| テーマ | 代表的な研究 | 要点 | 取り込むもの |
|---|---|---|---|
| フレームカーネル | Asterinas (USENIX ATC'25) | 単一アドレス空間で、unsafe を小さな特権フレームワークに閉じ込める。TCB は約14%、性能は Linux 並み | 言語の安全性によるカーネル内特権分離 |
| イントラリンガル設計 | Theseus (OSDI'20 ほか) | OS の不変条件を型に載せ、コンパイラに検査させる | 言語と OS を同時設計するときの中心的な考え方 |
| ハードウェア能力 | CHERI / CHERIoT RTOS (SOSP'25)、CHERIoT 1.0 (2025-11) | ポインタが境界と権限を持ち、ハードウェアが偽造を防ぐ | 長期目標:言語の能力をハードウェアまで一貫させる |
| データ中心 OS | Twizzler (USENIX ATC'20) | 永続メモリをオブジェクト空間として扱い、ポインタはオブジェクト相対 | 「ファイル」ではなく「永続する値」を中心にする |

## 3. 先行事例:「OS のための言語」の歴史

| 年代 | 言語 → OS | 特徴 | Scull との関係 |
|---|---|---|---|
| 1961 | ESPOL → Burroughs B5000 MCP | ハードウェアと高級言語の共設計 | 言語による保護の源流 |
| 1972 | C → Unix | Unix を書き直すために C が作られた | 最も成功した例 |
| 1987 | Oberon → Oberon System | Wirth と Gutknecht の2人で言語・OS・GUI まで作った | 個人規模で完成させる手本 |
| 1995頃 | Limbo → Inferno | Bell Labs が Inferno 用に作った言語 | 言語と OS を同時に配布する例 |
| 2003– | Sing# → Singularity | 言語の型安全でプロセスを分離。チャネル契約 | フレームカーネルの先祖 |
| 2004–2012 | BitC → Coyotos | 能力ベースのマイクロカーネルを検証するための言語。2012年、設計上の根本的欠陥を理由に開発終了 | 同じ方向の試み。失敗の教訓 |
| 2008–2015 | M# → Midori | Singularity の後継。**オブジェクト能力でアンビエント権限をなくし**、変更可能な static 変数も禁止 | Scull の中核に最も近い先行事例 |
| 2016 | Cogent → seL4 上のファイルシステム | 検証しやすいファイルシステム用の言語 | 検証レイヤの参考 |

### Midori との違い(Scull に残る独自性)

「言語の能力 = OS の権限、アンビエント権限なし」は Midori が大規模に実現済み。Scull の独自性は次の点に絞られる。
- 能力をオブジェクトではなく**エフェクトとして型に書き、ハンドラで処理する**。システムコール自体がエフェクトで、ハンドラを差し替えればサンドボックスやモックになる。
- Singularity・Midori は GC 前提の C# 系。Scull は**値セマンティクス + 参照カウントで GC なし**。
- 2020 年代の型理論(Effekt、キャプチャ検査)と CHERI を土台にできる。

### 教訓
- **BitC**:型システムに野心を詰め込みすぎると、OS にたどり着く前に止まる。最初の型システムは小さく保つ。
- **Oberon**:機能を削ってシンプルにしたから、少人数で最後まで作れた。
- **必読**:Joe Duffy の Midori ブログ連載(特に *Objects as Secure Capabilities*)、Wirth の *Project Oberon*。

## 4. 言語 Scull の設計

```
// 能力は型に現れる。Console を持たない関数は出力できない
fun greet(name: String) / {Console} {
  Console.print("hello, " ++ name)
}

// 値セマンティクス:inout は一時的な可変アクセス(射影)
fun bump(x: inout Int) { x += 1 }

// ハンドラで能力の実装を差し替える(テスト・サンドボックス)
try { process_order(order) } with Clock {
  def now() = Time(2026, 11, 8)
}

// unsafe も能力。Raw を持つのは信頼された基盤モジュールだけ
fun mmio_write(addr: PhysAddr, v: U32) / {Raw} { ... }
```

注:上は構想段階の書き方。Scull 0 では `uses` 節と `handle ... by ...` を採用した(`scull0/01_scull0_implementation_spec.md`)。

設計方針:
1. **アンビエント権限なし**:グローバル変数経由の副作用を禁止する。
2. **unsafe = `Raw` 能力**:どこで使えるかを型と依存関係で監査できる。
3. **ハンドラはワンショットが基本**:例外・ジェネレータ・async はワンショットで足りる。マルチショットは将来の拡張。
4. **トレーシング GC なし**:値型 + 一意所有 + 参照カウント (Perceus)。
5. **仕様構文の予約**:`requires` / `ensures` / `ghost` を予約し、最初は実行時アサートとして扱う。

## 5. 利点と代償

### 優れている点(保証)
1. **シグネチャを見れば、関数にできることの上限が分かる**。依存ライブラリに必要な能力しか渡さなければ、サプライチェーン攻撃(xz-utils 型のバックドアなど)を防げる。
2. **unsafe を使える範囲が型で限定される**。安全性を確認すべきなのは `Raw` を持つ基盤部分だけ。
3. **「別の場所で書き換えられていた」バグが起きない**。データ競合もない。ライフタイム注釈も不要。
4. **GC で止まらない**。カーネルやリアルタイム処理にも使える。

### 便利な点(日常)
1. テスト用の差し替え(時刻・乱数・ファイル・ネットワーク)がハンドラで済み、DI の仕組みが要らない。
2. サンドボックスが数行で書ける。
3. ログ・トレース・リトライを、元の関数を変えずに外から付けられる。
4. 例外・ジェネレータ・async が1つの仕組みになり、関数の色問題を避けられる。
5. 値なので、コピー・比較・保存・プロセス間送信がそのままできる。
6. ドライバの MMIO 能力をモックにすれば、実機なしでホスト上でテストできる。

### 代償
- 能力の受け渡しが冗長になりやすい(能力ベースのシステムで昔から指摘される問題)。→ §6 の方針で対処する。
- 参照がないので、木やグラフは配列とインデックスで表す必要がある。
- エフェクトハンドラの効率的なコンパイルは難しい。
- 学習資料が少ない。

## 6. AI 時代の設計方針

- AI がコードを書けば、能力を受け渡す**記述の手間**はほぼ問題でなくなる。呼び出し元へ能力を伝播させる作業は機械的で、型エラーが正確なので、AI が確実に直せる。
- 手間は「書く」から「読んで確認する」へ移る。**権限を渡してよいかの判断は人間が行う**。
- 明示的な能力は、AI が書いたコードのレビューで大きな利点になる。シグネチャと能力の差分を見るだけで、最悪何が起こりうるかが分かる。
  ```
  - fun summarize(doc: Doc) -> String
  + fun summarize(doc: Doc) / {Net} -> String   ← なぜ要約に通信が?
  ```
- リスク:AI はコンパイルを通すために広すぎる能力を渡しがち(`Dir` で足りるのに `Fs` を渡すなど)。言語とツールの側で次の対策を入れる(Sweep 原則)。
  - 狭い能力(`Dir`、`ReadOnlyFile` など)を標準で用意する
  - 受け取ったのに使っていない能力を警告する
  - モジュールごとに能力の一覧を置き、変更がレビューで必ず目に入るようにする
- **原則:能力の変化が差分で目立つことを、推論による省略より優先する。**

## 7. 文法の設計

### 進め方
1. **意味を先に決め、文法は後にする**(BitC は意味の設計に集中するため Lisp 風構文のままにした)。
2. **サンプルプログラムを10本書く**:hello world、ファイルの行数を数える、時刻を固定するテスト、二分木の挿入、例外とジェネレータ、UART ドライバなど。迷った箇所が決めるべき項目になる。
3. **迷った箇所を決定リストにする。**
4. **EBNF で書き下す**(最初は1ページ程度)。
5. **Rust で手書きの再帰下降パーサーを作り、使って直す**。文法は後から変えやすく、意味は変えにくい。

### 原則
- 奇抜さは新しい概念(能力、ハンドラ)だけに使い、それ以外はよく知られた書き方を借りる。
- 先頭のキーワードで構文の種類が決まるようにする(パーサーも人間も読みやすい)。
- 同じことを書く方法は1つに絞る。
- 重要なもの(能力)は目立たせ、よく使うものは短くする。

### 主な決定項目とおすすめ(未決)

| 項目 | おすすめ |
|---|---|
| 全体の系統 | Rust・Swift 風の C 系(波括弧) |
| 能力の書き場所 | 引数の直後 `/ {Fs}`(差分で目立つ) |
| 受け渡し規約 | `let` / `inout` / `sink` / `set` を引数の前に(Hylo と同じ) |
| ハンドラ | `try { } with Eff { }` |
| ジェネリクス | `[T]`(`<T>` は比較演算子と紛らわしい) |
| 式と文 | if を式にする |
| 文の区切り | 改行 |

```
fun count_lines(file: ReadOnlyFile) / {Fs} -> Int {
  var n = 0
  for line in file.lines() {
    n += 1
  }
  n
}

fun insert[T: Ord](tree: inout Tree[T], x: sink T) { ... }
```

```
fun_decl   = "fun" IDENT generics? "(" params ")" effects? ("->" type)? block ;
effects    = "/" "{" IDENT ("," IDENT)* "}" ;
param      = convention? IDENT ":" type ;
convention = "let" | "inout" | "sink" | "set" ;
```

## 8. OS Coxless の設計

```
アプリ (Scull)      perform Fs.read(obj, buf)   ← 型の上ではただのエフェクト
   ▼
ハンドラ層          サンドボックス / トレース / モックを差し込める
   ▼
サービス (safe)     FS・ドライバ・スケジューラ ― Raw を持たない
   ▼
基盤 (Raw)          ページテーブル・割り込み・コンテキスト切替 ― 小さく、検証対象
   ▼
RISC-V (QEMU virt)  [将来] CHERI 能力
```

- **能力の一貫性**:型の能力 (`/ {Fs}`)、カーネルのハンドル、(将来は)CHERI のハードウェア能力が、同じ概念の層になる。
- **サンドボックスが言語機能になる**:信頼できないコードは、制限付きハンドラの中で動かすだけ。
- **ライブアップデート**:Theseus のように、状態を持たない小さなコンポーネントの集合にすれば差し替えられる。
- **捨てるもの**:POSIX 互換、グローバルなファイル木、アンビエント権限。
